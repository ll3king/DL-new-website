# SMS 规划二次对齐（基于批注后的收敛版）

最后更新：2026-04-24  
状态：Planning Draft  
目的：基于上一版文档的批注，重新收敛当前 SMS 方案讨论的边界、修正点和下一步聚焦问题。

## 1. 当前总判断

基于已批注内容，当前 SMS 方案不应进入“完整系统设计”阶段，而应停留在更克制的前期定义状态。

当前最合理的项目判断是：

- SMS 仍未形成正式可用功能
- 当前不宜把仓库内已有 SMS 痕迹视为既定正式能力
- 当前不宜过早冻结 contract、数据模型、状态机和人工接管细节
- 当前更应先验证真实网关行为，再反推最小可行设计

一句话总结：

`当前 SMS 方案仍处于前期定义阶段，应先验证 Telerivet 的真实 webhook/API 行为，再围绕“只处理高意向 booking sms”的原则，定义一个足够轻的 SMS booking handler。`

## 2. 基于批注后的主要修正

### 2.1 不应默认“所有短信都进入系统” （对的， 一定要 在源头就 判断 高意图booking）

上一轮方案默认所有 SMS 都会经过系统链路，这一点现在需要修正。

你提出的关键问题是：

- 是否只有高意向 booking 相关短信才送入 adapter / handler
- 是否不是每条短信都需要系统处理

这个问题目前尚未定论，但已经足够明确：

`“所有短信自动化处理”不应再作为默认前提。`

### 2.2 Conversation Service 的定义仍不清晰

上一轮用了 `Booking / SMS Conversation Service` 这个表述，但你质疑了它的职责边界：

- 它是否要做 booking intent 识别 （来到这里的 应该都是 高意图 booing request， 所以核心工作是跟进 并 确认booking）
- 它是否要接网站 AI 大脑 （一定要接入， 这才是我们的核心， 还是一样的 逻辑， 重复 利用 AI chat bot 的booking 逻辑）
- 它是否应该只是执行 booking rules （一定是执行 同一套booking rules， 记得 在 booking system 里 挂起 manual review 的booking就好）
- 它主要是负责回复和推进 booking request，还是要承担更大的对话逻辑

这说明：

`当前还不能把这一层定义成完整 conversation engine。`

更可能的方向是：

- 第一版不是“短信 AI 助理”
- 第一版更像“短信 booking handler”（本来就是这个， 确定了， 这就是SMS 的核心功能，手机里还有很多的 supplier 消息， 所以一定要确保 精准）

### 2.3 Persistence / CRM 的设计必须继续收缩

你强调了两个关键约束：

- 不要为 SMS 额外写太多冗余客人信息
- 已经在现有 CRM 记录过的信息，未来应尽量复用，不重复询问 （对， 还要自然点， 像人类一样， 但这个思考部分 应该是重复利用 我的 AI 大脑，具体的优化 更新应该是 独立 分支 上改动的 东西了， 这里过度复杂思考）

因此当前判断是：

- SMS 线程层只保存最少必要上下文
- 客人长期信息仍应复用现有 booking / CRM 数据
- 短信系统不应单独发展成新的重型客资系统

### 2.4 数据模型和状态机还没有压到足够轻

你对 `SmsThread`、`SmsMessage` 和状态机都提出了相同疑问：

- 这是否真的是最简洁高效的设计
- 有没有仍然不必要的复杂度

因此当前结论是：

- 还不能冻结最终数据模型
- 还不能冻结最终状态机
- 需要进一步压缩，再讨论是否落地

### 2.5 不能太早冻结内部 contract

你明确提出：

- 先真实测试 Telerivet 的 webhook API / send API
- 再建立适合的 adapter 接口

这意味着：

- 现在最多只能提出“候选 contract”
- 还不能称之为“正式冻结”

这是当前需要保留的关键原则。


（后面 的 东西我就不看了， 估计也会变动， 你先对齐上面的 批注 信息， 找出 可行性 方案， 并再 深度 思考 telerivet developer guide， 里面说到了 running code on your own servers， 这里是不是说明我们可以合并telerivet 和 adapter的 功能。 ）

## 3. 当前不宜急着定下来的内容

基于以上修正，下面这些内容现在都不适合正式冻结：

- 最终 `SmsThread` 字段集
- 最终 `SmsMessage` 字段集
- 最终状态机
- 最终 inbound / outbound / status contract
- CRM 复用的具体细节
- 人工接管后的系统内流转细节

这些内容都应在真实网关测试之后再收口。

## 4. 当前可以先定下来的内容

目前已经可以先确认的内容有：

- `Tailscale` 从正式方案中移除
- `Telerivet` 是当前优先验证的正式网关候选
- `Cloudflare adapter` 仍是目前最合理的正式入口方向
- 第一版设计必须保持简洁和克制
- 不做复杂客服后台
- 不做本地常驻服务
- 不做过早的平台化抽象

## 5. 当前重新收敛后的设计方向

### 5.1 当前不应再把系统理解成“完整短信会话系统”

更准确的理解应当是：

- 先做一个足够轻的 SMS booking 处理链路
- 不急着做泛化 conversation engine
- 不急着做泛化 AI assistant

### 5.2 第一版更像 SMS booking handler

当前更合理的表述不是：

- `SMS conversation service`

而是：

- `SMS booking handler`

这表示它第一版的职责应收敛为：

- 接收已进入系统范围内的 booking 相关短信
- 推进 booking request
- 复用既有 booking rules
- 生成有限模板回复
- 写入最少必要数据

而不是承担完整自由对话理解。

## 6. 当前最重要的 3 个待讨论问题

下一轮不应再继续泛谈整套系统，而应只聚焦这 3 个问题。

### 6.1 哪些短信进入 booking flow

这是当前最关键的问题。

需要明确：

- 是不是只有明确 booking request 才进入自动处理
- 普通咨询、闲聊、无效短信是否直接留给人工或忽略
- “高意向 booking sms”的标准应如何定义

当前倾向是：

`不是所有短信都自动化，只把明确 booking request 纳入系统。`

### 6.2 第一版是否不接 AI 大脑

需要明确：

- 第一版是否只做规则驱动
- 是否只做有限模板回复
- 是否完全不接网站现有 chat AI 大脑

当前倾向是：

`第一版不应默认接网站 AI 大脑。`

### 6.3 SMS 最小落库范围

需要明确：

- 哪些短信信息必须存
- 哪些信息应直接复用现有 CRM
- 哪些字段可以完全不加

目标是：

`先做最少必要留痕，不额外造重型短信数据层。`

## 7. Tailscale 的当前定位

基于当前批注后的收敛，`Tailscale` 不再进入正式方案。

当前标准表述应为：

- 不纳入正式 SMS 方案
- 不作为主入口设计的一部分
- 后续如确有极短期调试用途，可另行单独考虑

但对当前正式 planning 来说：

`Tailscale 已从主方案中排除。`

## 8. 当前对 Telerivet 的角色理解

当前建议仍然是：

- `Telerivet` 作为候选正式网关
- 负责真实手机短信收发
- 负责路由、同步和状态能力

但需要补充一个关键待确认点：

- 是否所有短信都通过系统处理
- 还是只有部分高意向 booking sms 被送入系统

因此当前对 Telerivet 的角色定义还不能完全写死。

## 9. 当前对 Adapter 的理解

目前仍保留 `Cloudflare adapter` 这个方向，但应进一步瘦身理解。

当前建议是：

- Adapter 只做入口协调和协议转换
- 不承担 booking 核心业务
- 不承载复杂会话逻辑
- 其接口形态应在真实测试 Telerivet 后再定

因此：

`Adapter 的存在方向可以先保留，但接口细节不应现在冻结。`

## 10. 当前对 SMS 数据层的理解

当前不建议再继续扩展短信数据结构，而应先保持保守：

- 只记录真正必要的线程/消息上下文
- 尽量复用现有 booking / CRM 数据
- 避免重复采集已知客人信息
- 避免让 SMS 方向长成独立重型 CRM

## 11. 当前对人工接管的理解

当前方向仍可保留为：

- 第一版人工查看和手动回复入口先依赖 `Telerivet inbox`

但要注意：

- 不应为了“可能发生的人工长链路”提前扩展大量系统复杂度
- 很多短信在人类接手后，可能并不会产生后续系统动作
- 只有能形成 booking request 的部分，再按 booking 规则落系统

因此：

`人工接管的设计应保持克制，不因边缘情况提前扩展系统。`

## 12. 当前一句话对齐结论

`SMS 方案当前还不该进入完整系统设计阶段，而应先以 Telerivet 为候选网关，验证真实 webhook/API 行为，再围绕“只处理高意向 booking sms”的原则，定义一个尽可能轻的 SMS booking handler。Tailscale 从正式方案中移除，复杂状态机、复杂客服后台、多供应商抽象和过早 contract 冻结都暂不进入。`

## 13. 下一步建议的讨论顺序

在继续讨论之前，建议按下面顺序推进，而不是同时展开：

1. 先讨论：哪些短信才进入 booking flow
2. 再讨论：第一版是否完全不接 AI 大脑
3. 再讨论：SMS 最小落库范围

## 14. 待批注的关键问题

建议你重点批注下面这些问题：

1. 是否确认“不是所有短信都进入系统”
2. 是否确认第一版定位应从 `conversation service` 调整为 `SMS booking handler`
3. 是否确认第一版不默认接网站 AI 大脑
4. 是否确认短信数据层只保留最小必要留痕
5. 是否确认 Tailscale 已从正式方案中移除
6. 是否确认 contract 现在还不应冻结
